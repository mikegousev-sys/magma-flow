# Скоростемер потока никелевого расплава — состояние проекта

Документ для передачи в новый чат. Приложите его вместе с последними файлами
кода (см. список ниже) первым сообщением.

## 1. Что это за проект

Система измеряет скорость потока расплава в жёлобе и уровень расплава,
бесконтактно, тремя независимыми способами:
- **фотодиоды** (4 шт, корреляционный метод) — основной канал скорости;
- **камера** (профиль яркости вдоль потока) — независимая проверка скорости
  + измерение уровня по геометрии зеркала;
- **стереопара камер** (триангуляция) — ещё одна независимая проверка обеих
  величин, готова как модуль, но пока не подключена к общему процессу.

Железо: Arduino Nano (фотодиоды) → Raspberry Pi 5 (сервер) → клиент.
Отдельно — Raspberry Pi + камера MV-MIPI-SC130M → процесс зрения → свой клиент.

Проект разделён на две категории по требованию пользователя:

**Дополнение — редактируется свободно:**
`magma_capture.hpp`, `magma_veye.hpp`, `magma_exposure.hpp`, `magma_edge.hpp`,
`magma_level.hpp`, `magma_flow.hpp`, `magma_config.hpp`, `magma_broadcast.hpp`,

Ключевой архитектурный принцип: **зрение — полностью самостоятельный процесс**,

ни одной правкой ради зрения — это осознанный выбор, а не недосмотр.

## 3. Ключевые физические параметры (определены в разговоре)

- Геометрия жёлоба: дуга R150 мм, рабочий максимум уровня 105 мм.
- Расстояния между фотодиодами вдоль потока: 75, 50, 75 мм (6 баз всего).
- Камера для скорости/уровня: MV-MIPI-SC130M, глобальный затвор, 1280×1024.
- Угол камеры к плоскости расплава β ≈ 31° (определён по опорному снимку
  через две линии известной длины — вдоль и поперёк потока).
- Масштаб при объективе 30 мм: ≈0.4135 мм/пиксель на дистанции 4 м
  (пересчитано 2026-09-14 с исходных ≈0.248 мм/px при 50 мм — масштаб
  обратно пропорционален фокусному расстоянию при той же дистанции и
  матрице; изменено в `magma_vision.conf`, `magma_vision.cpp` и
  `magma_stereo.hpp`, где заодно поправлен `focal_length_mm`).
- Стереопара: база 125 мм, **вдоль потока** (не поперёк — важное уточнение,
  изменившее формулы проекции в magma_stereo.hpp).
- Диафрагма F/6, расплав ярче ожидаемого — насыщение матрицы наступает
  за десятки-сотни микросекунд, смаз от движения почти всегда пренебрежим.

## 4. Ключевые алгоритмические решения и их причины

- **Многобазовая корреляция** (и для фотодиодов, и для камеры): перебор
  скоростей-кандидатов, вклады со всех баз/интервалов складываются ДО поиска
  пика. Устраняет проскок цикла и ложный пик на нулевой задержке — обе
  проблемы реально наблюдались на архивных данных.
- **GCC-PHAT** вместо обычной корреляции — устойчивее к доминирующей
  синхронной помехе.
- **Вычитание неподвижного фона** обязательно для камеры — без него
  корреляция цепляется за неподвижную корку на стенках и даёт ноль.
- **Медиана**, а не среднее, для сглаживания секундных/серийных оценок —
  устойчива к единичным выбросам.
- **Горячая перезагрузка настроек** (`magma_config.hpp`) — все параметры
  наладки (полосы выборки, метки, углы, границы выдержки) меняются без
  перезапуска процесса зрения; кроме адреса/порта вещания (требует
  перезапуска, это единственное осознанное исключение).
- **Адаптивная выдержка** (`magma_exposure.hpp`) — держит настройки при
  пустом жёлобе (иначе первая серия после прихода расплава ушла бы в
  насыщение), приоритет выдержки над усилением до предела по смазу.
- **Триангуляция скорости по стереопаре** — НЕ через 3D, а через разность
  пиксельных диспаратностей метки (неподвижной) и текстуры (движущейся);
  разность делится на Δt между кадрами двух камер. Требует известного Δt —
  метод работает БЛАГОДАРЯ рассинхронизации камер, а не вопреки ей.

## 5. Нерешённый физический вопрос

Истинная скорость потока — **1.5 или 2.9 м/с** — не установлена. Прежние
логи допускали оба ответа из-за слишком большого пятна обзора фотодиодов
(≈120 мм при базах 50–200 мм). Рекомендовано сузить пятно щелевой диафрагмой
и/или сменить оптику. Независимая проверка через расход (сечение жёлоба ×
производительность) не проводилась — данных о производительности не было.

### USB gadget mode (выполнено 2026-09-14/15)

- На плате физически один USB-C — используется одновременно и для питания,
  и (через `dwc2` в peripheral-режиме) для данных. Линии данных на нём
  РАЗВЕДЕНЫ (проверено практически: COM-порт и Ethernet-gadget видны на
  хосте) — уточнение к общему мнению «USB-C Pi5 только для питания».
- **Нельзя** одновременно подавать питание от штатного блока И получать
  VBUS от USB-порта хоста через тот же кабель — конфликт двух источников
  5В вызывает аварийное отключение (красный LED). Питание должно идти
  только с одной стороны.
- Питание с порта хоста работает надёжно только через **задний** USB-C
  порт материнской платы ПК (напрямую на плате) — передний (через шлейф
  на переднюю панель корпуса) не даёт достаточного тока, вызывает
  ту же аварию (недостаточно тока → undervoltage → отключение).
- Настройка (уже применена и переживает перезагрузку):
  - `/boot/firmware/config.txt`: `[pi5]` → `dtoverlay=dwc2,dr_mode=peripheral`;
    `[all]` → `usb_max_current_enable=1` (снимает софт-ограничение на
    ВЫХОДНОЙ ток USB-портов Pi при отсутствии официального PD-блока; НЕ
    влияет на входное питание от хоста).
  - `/boot/firmware/cmdline.txt`: добавлен `modules-load=dwc2,g_ether`
    (сразу после `rootwait`).
  - Резервные копии обоих файлов: `*.bak-pre-gadget` в том же каталоге.
  - `usb-gadget-net.service` (systemd, свой юнит, НЕ NetworkManager —
    NM ждёт carrier и не поднимает интерфейс надёжно при загрузке):
    поднимает `usb0` и назначает статический `169.254.84.1/16` при каждом
    старте.
  - Windows-хост сам получает адрес автоконфигурации в той же
    169.254.0.0/16 подсети (APIPA) — админ-прав на стороне Windows не
    требуется.
- Подключение с ПК: физически кабель в **задний** USB-C порт материнки,
  затем `ssh mike@169.254.84.1`.

### Инцидент 2026-09-15: камера пропала после манипуляций с питанием/кабелями

- После серии сегодняшних отключений/переподключений камера перестала
  находиться (`mvcam 10/11 NOT FOUND`, I2C шины 10 и 11 пустые,
  `magma-vision` получал `errors:1, frames:0` на каждой серии).
  `vcgencmd get_throttled` показывал `0x50005` — было и историческое, и
  ТЕКУЩЕЕ undervoltage (бит 0).
- Причина: камеру физически переставили **с CAM0 на CAM1** во время осмотра
  шлейфа. `magma-camera-init.service` при загрузке не успевал её найти —
  гонка: I2C-пробинг сенсора после power-up происходит с задержкой, скрипт
  проверяет оба порта один раз и не переповторяет попытку.
- Диагностика: `media-ctl -d /dev/media1 -p` показал полностью собранную
  цепочку `mvcam 11-003b` → `csi2`, хотя `i2cdetect -y 11` в этот момент
  показывал только `UU` (занято драйвером, не отвечает на пробу) — то есть
  ядро уже держит устройство, просто наш скрипт проверял раньше, чем
  завершилась инициализация сенсора.
- Исправление (временное, вручную): `sudo systemctl stop magma-vision`
  (иначе `VIDIOC_S_FMT: Device or resource busy`) → повторный запуск
  `media_setting_rpi5.sh mvcam -fmt RAW8 -w 1280 -h 1024 -c 2` → `sudo
  systemctl start magma-vision`. После этого захват пошёл сразу
  (`frames:120, errors:0`).
- **Исправлено 2026-09-15:** `magma-camera-init.service` теперь запускает
  `~/magma/camera-init-retry.sh` — до 6 попыток с паузой 3с, пробует оба
  порта (`-c 2`) каждый раз, завершается успешно по фразе `set CAM. finish`
  в выводе скрипта; если камера не найдена после всех попыток — юнит всё
  равно завершается успешно (exit 0), чтобы не блокировать
  `magma-vision.service` (тот сам переоткрывает `/dev/video0` перед каждой
  следующей серией, см. `EnsureCameraOpen()` в magma_vision.cpp).
  Проверено настоящей холодной перезагрузкой: попытка 1 не нашла камеру
  (та самая гонка), попытка 2 (через 3с) нашла на CAM1 и настроила —
  `magma-vision` заработал сразу, без ручного вмешательства.
- Проверено остальное дерево проекта на похожие гонки/отсутствие retry:
  сетевые клиенты (`magma_client.cpp`, `magma_client_logging.cpp`,
  `magma_vision_client.cpp`) и UART в `magma_server.cpp` уже имеют
  встроенный retry на переподключение — доработка не нужна. Единственным
  местом без защиты от гонки при холодном старте был именно системный
  скрипт инициализации камеры (теперь исправлено).
